The Incident

A dual-homed Kali analyst VM was set up against an isolated Metasploitable target on a VirtualBox host-only network. A default Nmap scan against the target returned 23 open TCP services a large attack surface that needed to be triaged, validated, and reduced rather than just listed.

The Mission

Enumerate and prioritize the exposed attack surface, validate the highest-severity findings through actual exploitation rather than assuming severity from a CVE label alone, then remediate and verify the fix.

Before I Started

Which of these 23 open services are genuinely dangerous versus just old? Can I prove exploitability, not just flag a CVE? And what's actually safe to disable without locking myself out of the box?

Finding — Investigator's Reasoning

A version-banner scan alone would have flagged the outdated FTP service as one entry among many legacy services. Running the actual exploit against it and landing a root shell with uid=0(root) is what separated it from every other 'outdated software' finding on the host, and that distinction is what justified prioritizing it first in remediation.

Investigation Timeline

17:05
Initial recon — default Nmap scan against 192.168.56.102 identifies 23 open TCP ports.
17:13
Service/version scan — nmap -sV fingerprints vsFTPd 2.3.4, OpenSSH 4.7p1, Apache 2.2.8, and several other legacy services.
17:23
Vulnerability scripts run — nmap --script vuln confirms the vsFTPd 2.3.4 backdoor (CVE-2011-2523) plus weak/legacy TLS findings (POODLE, Logjam).
18:33
Exploitability confirmed — targeted ftp-vsftpd-backdoor script executes id through the backdoor, returning uid=0(root).
18:44
Exploitation — Metasploit's exploit/unix/ftp/vsftpd_234_backdoor launched against the target; interactive root shell obtained.
19:05
Baseline documented — pre-remediation re-scan run to record the starting state before any changes.
Remediation
Four services disabled via xinetd — Telnet (23), the exposed root shell (1524), UnrealIRCd (6667), and vsFTPd (21) — while SSH (22) was intentionally left untouched.
Verification
Re-scan confirms closure — port 21 no longer listening and CVE-2011-2523 no longer detectable.

Case Evidence

Initial recon — confirming the Kali analyst VM's dual-homed network setup before scanning the target.
Service/version scan — nmap -sV fingerprinting all 23 open ports, including vsFTPd 2.3.4 and several other legacy services.
Vulnerability confirmed — the targeted ftp-vsftpd-backdoor script proving CVE-2011-2523 is exploitable, with the backdoor shell returning uid=0(root).
Exploit staged — Metasploit's exploit/unix/ftp/vsftpd_234_backdoor module configured against the target.
Root shell obtained — interactive access after the exploit lands, confirming the CVE wasn't theoretical.
Post-exploitation enumeration — /etc/passwd and sudo -l confirming full root-level access.
Remediation applied — setting disable = yes in the xinetd service definition to close the vulnerable FTP service.
Fix verified — the follow-up nmap -sV -p 21 scan confirming port 21 moved from open to closed after remediation.

Method

How I Thought
Through This One

Question I Asked

"Which of 23 open ports actually deserves urgent remediation, versus just being old?"

Evidence

nmap -sV service/version banners, nmap --script vuln output, and the result of an actual exploitation attempt against the flagged vsFTPd service.

What I Initially Thought

My first pass treated the vsFTPd version mismatch as one flagged item among many outdated services on the host — a note to fix eventually, not an emergency.

What Changed My Mind

Running the Metasploit module against it and getting a root shell (uid=0) is what separated it from every other 'outdated software' finding — CVE-2011-2523 wasn't theoretical here, it was demonstrated.

Conclusion

A version banner and a validated exploit are not the same finding. Confirming exploitability is what let me rank remediation correctly instead of by CVE severity label alone.
