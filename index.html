Case 001 · Featured Investigation
Endpoint Intrusion Investigation
Digital Forensics
Incident Response
Memory Analysis

The Incident

A workstation triggered an EDR alert for an unrecognized process spawning from an unusual parent. The machine was isolated before further behavior could be observed live, which meant the answers had to come from a memory capture and disk artifacts not from watching it happen.

The Mission

Determine how initial access was gained, what executed after that, whether persistence was established, and what if anything left the host.

Before I Started

What happened? How did the attacker get in? What actually ran? Was persistence set up, and did anything leave the network?

Finding — Investigator's Reasoning

Volatility flagged a process I initially assumed was the primary execution mechanism, since it matched the alert almost exactly. Cross-referencing its parent-child relationship against the loaded-module list told a different story: it was a decoy, spawned to draw attention while a second, quieter process handled persistence. That reframed the entire timeline below.

Investigation Timeline

Initial access — phishing-delivered dropper executes on host.
10:16

10:18

10:22
Persistence identified — scheduled task tied to the secondary process.
10:31
Evidence collected — memory image, disk artifacts, and registry hives preserved.
10:45
Investigation completed — findings handed off for containment and reporting.

02 / Method

How I Think

Not a highlight reel the actual reasoning behind one finding, including the part where I was wrong first.

Question I Asked

"Is this process actually malicious, or is it a legitimate Windows process with an unusual name?"

Evidence

Process tree from the memory capture, parent-child relationships, and loaded module list from the same image.

What I Initially Thought

The named process was the payload itself it matched the alert signature closely enough that treating it as the source felt reasonable.

What Changed My Mind

Its parent process didn't match any expected launch path, and a second process with matching module-load timing pointed to it being the actual mechanism the first was a decoy.

Conclusion

Treating the loudest indicator as the answer would have closed the case on the wrong finding. The quieter, correlated evidence is what actually explained persistence.
